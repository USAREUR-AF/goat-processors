Validate the correlation engines

Run them on your data, set them against your tracker, and show a better setting. Every claim is a number with a 95 % interval that anyone can measure again.

The correlate packs are scored against ground truth on generated scenarios and on public ship tracks. That is not the same as real sensors. If you have a tracker, a recording or an idea, this page is the way in. Python 3.12 and a clone are enough; nothing to install.

Compare your tracker

Write one events file per benchmark scenario and get your scores against every pack on the same scenarios, with the same rule for "better".

Suggest an improvement

Change a setting, measure it in one command, and open a pull request with the result. CI measures it again.

Where things stand

The default pack, assign-time, scores F1 0.947 (0.936 to 0.957) on the 500 random scenarios of the held-out evaluation set. F1 runs from 0 to 1: does the output put two tracks together exactly when they are one object?

Validate on real data

Real recordings have no ground truth, so the check is in two parts: is the feed fit for correlation, and do different correlators agree on it? Where they disagree is where to look.

1. Record

The runner records every report and tick when its config sets record.path and record.max_mb. Any other source works too: one JSON report per line, with track.source_id, uid, time_ms, lat, lon and, ideally, ce, the one-sigma error in metres.

2. Check the feed

python3 -I tools/feeds/feedcheck.py record.jsonl
python3 -I tools/feeds/feedcheck.py --demo overlap   # no data yet

Each source comes out ready, ready with warnings, or not ready: does it state its error, is that error honest, does its time go forward. With two sources, it says whether they see the same objects and whether fusion is actually exercised. Every check and its limit.

3. See where the packs agree

python3 -I tools/feeds/agree.py record.jsonl --with correlate-assign-time --with correlate-gnn --worst 5

Agreement is pairwise F1 of one output against the other: 1 when every pair of tracks is grouped alike. It is not accuracy. Two outputs can agree and both be wrong, so the ticks where they differ most, listed by second, are the useful part: look at those in your own tools.

4. Share the summary

python3 -I tools/feeds/feedcheck.py record.jsonl --rename --json > summary.json

The summary holds counts, rates, shares and medians, with the sources renamed s1, s2 and so on: no position, no track identifier, no time of day. Paste it into an issue with the "Performance result" form. Do not publish the recording itself.

Compare your tracker

Any tracker in any language can be scored, as the seven engines are: run it on the scenario files and write what it outputs at each tick.

# the 691 public tuning scenarios, each with its truth file
python3 -I tools/bench/bench.py generate --out build/bench/scenarios

# run your tracker on each scenario, write one events file per scenario, then:
python3 -I tools/review/compare.py build/my-tracker

A scenario file is a list of steps, each an ingest of one report or a tick. At each tick, write your whole picture, each output track with the reported tracks it holds:

{"engine": "my-tracker", "scenario": "random-01",
 "ticks": [{"now_ms": 1000, "tracks": [
   {"system": "T1", "members": ["radar/T3", "beacon/T3"], "lat": 0.98814, "lon": 0.94721}]}]}

compare.py scores every group whose scenarios all have an events file and sets it against assign-time, gnn and window (others with --against), measure by measure. Scoring one of our own packs this way gives its published numbers, which CI checks. To compare on your real data instead, pass your events file to agree.py as one of the --with outputs.

Suggest an improvement

A pack is a plain text file of settings. Copy one, change a setting, and measure it against the one you started from.

cp -r packs/correlate-assign-time packs/correlate-mine   # then edit pack.def
python3 -I tools/review/review.py try correlate-mine --against correlate-assign-time
python3 -I tools/review/review.py record my-change correlate-mine --against correlate-assign-time \
  --kind improve --question "..." --finding "..."

record writes one file under reviews/. Open a pull request with it and the pack. CI measures it again from your branch, a maintainer runs the held-out set, and the pull request says which measure decided. A setting that did not help is worth recording too, as kind measure: it saves the next person the same work. To change a method rather than a setting, open an issue first: methods change in all seven engines together.

What counts

ClaimNeeds
betterthe paired 95 % interval of the difference excludes zero, on the public tuning set, then confirmed by a maintainer on the held-out set
no worseno measure worse, by the same rule
reproducesthe published numbers measured again on your machine (review.py record ... --kind replicate)
works on real dataa feed check summary and an agreement result, with what was recorded and for how long
fastertools/perf/perf.py before and after, on one quiet machine

Do not put real positions, identifiers or recordings in an issue, a pull request or a test. Recorded data in the repository needs a public source whose license allows it. The held-out seeds stay with the maintainer so that nothing is tuned on them; they are published after each release and replaced.
